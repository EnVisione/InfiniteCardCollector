## Purpose and Ownership

This phase delivers direct same-server trading as a server-owned, recoverable two-profile operation. Eligible players must be able to opt out of incoming requests, invite or decline without penalty, build exact revisioned offers from explicitly tradable items, inspect both sides without custom text, review nonauthoritative value and only-copy warnings, ready the exact offer, complete a visible countdown, and receive matching durable receipts and recent history. At every point, one item has one effective owner and no disconnect, shutdown, throttle, stale request, replay, concurrency race, or partial profile write may duplicate, lose, expose, or silently mutate an item.

The phase canonically owns `CORE-REQ-020`. It consumes the network, profile, transaction, inventory, client, security, configuration, and isolated two-client contracts delivered by earlier phases. It produces the direct-trade state machine, persistent journal, per-profile settlement receipts, locked-item mutation boundary, reconciliation-before-writable-play gate, support evidence, trade-specific feature controls, and an auditable trade-readiness record.

`DEC-005` permits exactly two public release outcomes, enabled or visibly disabled. This phase does not select the public outcome or turn `TradeEnabled` on. It records either `enablement_candidate` after every mandatory phase-owned gate passes with no known defect, or `visibly_disabled` after those same mandatory implementation and recovery gates pass but enablement is not being advanced. Phase 009 may enable new trading only after the exact frozen candidate also passes `EXT-011` authorization and production smoke; otherwise new trading remains visibly disabled while prepared-journal reconciliation continues. The disabled outcome is a verified release fallback, not a waiver of the implementation, recovery, or evidence required by this phase.

The master plan owns product scope, requirement meaning, owner decisions, external prerequisites, global topology, and the completion endpoint. This file owns only the dependency-ordered execution of `CORE-PHASE-006`. It cannot authorize cross-server listings, player currency transfer, real-money value, wagers, custom trade text, public release, or future content.

- CORE-REQ-020: Define effective ownership by durable state so a profile copy cannot be usable merely because one side has settled first. Before prepare, the original profile is effective owner. - CORE-REQ-020: Reconcile prepared, settling, committed, partially unlocked, and partially receipted journals before writable play. - CORE-REQ-020: Issue immutable matching completion receipts, append bounded recent history to both profiles, preserve permanent discovery, update current ownership projections, and expose a permission-checked support evidence view keyed by receipt or trade ID without raw profiles or arbitrary text.

- CORE-REQ-020: Implement trade-specific emergency controls. ## Architecture and Implementation Boundaries

### Ownership and Dependency Direction

`TradeService` owns invitation lifecycle, participant exclusivity, transient offers, revisions, readiness, countdown, trade locks, journal coordination, settlement orchestration, completion receipts, history projection, and reconciliation state. It calls typed Profile, Transaction, Inventory, Collection, Network, Security, Analytics, configuration, and client-message interfaces. It does not reach into another service's mutable tables, write DataStore keys outside the storage abstraction, calculate real-money value, trust client time, or let UI animation drive state.

`ProfileService` owns session acquisition, writability, profile updates, save behavior, safe mode, and the recovery-before-ready gate. `TransactionService` owns each idempotent per-profile mutation and operation receipt. `InventoryService` owns instance and stack authority, provenance, copy counts, locks, current ownership, and mutation eligibility. `TradeService` coordinates these owners through explicit methods and durable journal state; it does not duplicate their authority.

The network gateway validates each Trade envelope before routing. The client controller submits only participant intent and renders server messages. `TradeController` and `StarterGui/App/Trade` cannot infer an accepted invite, offer edit, Ready state, countdown completion, prepare, settlement, completion, cancellation, or recovery from local time or animation.

### Configuration, Eligibility, and Social Boundaries

All eligibility and safety values are server configuration. At minimum, configuration contains account-age days, trusted active seconds, tutorial completion requirement, profile mode, supported contract version, newly obtained item lock, request expiry, request cooldown, offer item limit, countdown seconds, receipt history bound, action token buckets, global burst limit, value-band version, asymmetry thresholds, retry policy, journal retention, and `TradeEnabled`.

The launch defaults fixed by the source are at least seven account days, at least two active hours, completed tutorial, fully loaded writable profile, ten-minute new-item lock, five-second request cooldown, twelve offered entries per side, five-second countdown, and one hundred recent receipts. Request expiry is a required finite positive bounded configuration value; the selected value and boundary behavior must be documented and tested rather than client supplied.

A request is eligible only when `TradeEnabled` accepts new work; inviter and target are distinct, present in the same server, and using compatible clients; both profiles are fully loaded and writable; recovery has completed; neither has unresolved journals, orphan locks, another pending invite, or another active trade; account-age, active-time, durable trade-tutorial completion, social-policy, and security gates pass; the target permits incoming trade requests; and the inviter has rate capacity. Acceptance revalidates every condition.

The trade tutorial uses fixed localized copy and the existing server-owned tutorial persistence boundary. It presents allowed and forbidden value, exact item review, only-copy and approximate-value warnings, edit-driven readiness reset, the five-second countdown, immutable receipts, history, and receipt-based reporting. Tutorial completion is an idempotent durable operation or checkpoint result. Duplicate identical completion returns the saved result, conflicting or stale completion fails, and a modified client cannot claim unobserved checkpoints or directly set eligibility.

The incoming-request setting prevents unsolicited invitations without exposing private reasons for unavailability. A player who opts out may still initiate a trade if otherwise eligible. Decline, expiry, opt-out, ordinary busy state, and ineligibility are not punishable security events. Malformed, impossible, conflicting, or abusive patterns may produce bounded sanitized signals.

### Tradable Item and Lock Contract

The tradability registry is a versioned server-owned map from item category and provenance to normalized offer behavior. Launch cards and unbound Joker instances transfer by opaque UID. Arcana inventory items may transfer only through a stable Arcana ID and bounded positive integer quantity reserved from the authoritative stack. Souls remain disabled until future release. Unknown types fail closed.

Every offered unit must be currently owned by the offering participant, enabled for trade, past its new-item lock, not bound, not protected by provenance, not equipped, not favorite, not grading, not an Arcana or progression target, not ordinarily locked, not already trade-locked, not pending in a pack or bind operation, and not claimed by another durable operation. The last owned copy may be offered only with an explicit only-copy warning and final review; ordinary auto-salvage protections do not silently prohibit a deliberate validated trade unless the versioned tradability policy says otherwise.

Each offer claim records trade ID, participant side, normalized entry identity, quantity where applicable, lock version, and lifecycle class. Pre-prepare claims prevent concurrent mutation but remain cancellable and recoverable. Prepared and settling claims are durable and noncancellable by clients. A competing claim for the same instance or stack units fails without changing either trade.

Deck, Inventory, Pack, Progression, Arcana, Joker, and any future item-consuming service must consult the authoritative lock boundary. Equip, unequip where it would mutate the offered instance state, favorite or ordinary lock changes that conflict with the offer, bind, salvage, Grade, Trait, Arcana, pack, retrade, and other state changes reject with a stable lock reason. Presentation cannot optimistically show success.

### Offer Revisions, Review, Warnings, and Countdown

An offer is a bounded ordered set of normalized entries. The server owns its monotonic revision. The canonical hash covers trade ID, both participant IDs or stable sides, both normalized offers in canonical order, quantities, item version or immutable property hashes, journal schema, offer schema, tradability version, relevant catalog version, and warning/value configuration version. Presentation order may differ, but canonical serialization and hash cannot depend on table iteration.

Every accepted add, remove, or quantity edit increments the revision exactly once, recomputes the hash, clears both Ready flags, and cancels any countdown. A rejected edit changes nothing. Concurrent edits serialize; clients receive the accepted revision and full bounded current offer projection or a narrow patch that cannot conceal an intervening change.

Both sides receive exact stable item properties required for informed review, the offering side's current owned count, collection or discovery status, transfer consequence, only-copy status, approximate game value band, and configured material-asymmetry warning. Value bands use server configuration and stable catalog properties, not player text, external markets, Robux, money, or client claims. UI copy must say that the band is approximate guidance and does not certify equal value, demand, rarity, or fairness. Warnings do not override hard eligibility and do not create an authoritative appraisal.

A Ready action names the exact current revision and offer hash. Both current Ready states begin one authoritative five-second countdown. The UI continuously shows exact offers, revision, warnings, readiness, countdown, and connection state. Any edit, disconnect before prepare, participant or item ineligibility, feature disable, incompatible configuration change, or hash mismatch clears readiness and cancels the countdown. Client countdown completion is cosmetic and cannot prepare a trade.

### Persistent Journal and Prepare Boundary

The persistent journal is the only authority for a cross-profile trade after prepare. It contains at least trade ID, schema version, journal version, state, both user IDs, both exact normalized offers, original owner map, offer hash, relevant catalog and configuration versions, prepared timestamp, committed timestamp, per-side settlement state and step number, per-side operation and receipt identity, completion receipt identity, error code, retry state, and bounded support metadata. It contains no arbitrary player text or raw profile.

Prepare revalidates both profiles, offers, quantities, locks, revisions, hash, feature state, configuration version, and absence of conflicting journals. The immutable prepared journal is persisted before a transfer can become effective. Partial provisional-lock creation or a failed journal write remains a pre-prepare cancellation case and unlocks through idempotent cleanup. A durable prepared journal makes the transfer noncancellable by clients and discoverable by either profile load or a recovery worker.

Journal writes use optimistic version checks and bounded retry with jitter. Repeating an identical transition returns current state. An attempted backward, skipped, or conflicting transition fails closed and records bounded evidence. Unknown future journal versions remain nonwritable and require compatible migration or operator review; they are never guessed or deleted.

### Two-Profile Settlement and One Effective Owner

Roblox DataStore does not provide a transaction across two profile keys. Settlement therefore advances one immutable prepared transfer through stable idempotent steps. Step numbers are assigned by the versioned settlement contract and cannot be client supplied or reused for a different payload. Each profile-side operation ID is derived from the trade ID, side, step number, and schema version.

Each side operation verifies the journal, expected original and incoming items, locks, offer hash, profile identity, processed trade evidence, and current revision. It applies the exact remove and receive set once, records a receipt, increments the profile revision, saves immediately, and returns the committed result on identical replay. Reuse with a different offer, side, step, quantity, or hash rejects and quarantines the trade.

Effective ownership is resolved from durable trade state rather than from whichever profile document was read in isolation:

1. Before durable prepare, the original profile is the effective owner and any offer claim only blocks mutation.
2. From `prepared` through `settling`, the journal is the sole effective ownership authority and reserves every offered unit. Neither original nor destination profile may equip, alter, consume, transfer, or expose it as usable, including after one side operation has saved.
3. After the journal is durably `committed`, each destination profile is the effective owner according to the exact prepared offer. Repeated settlement or unlock work cannot change that result.
4. `completed` records delivery of receipts, history, projections, and cleanup. Client acknowledgement and animation never affect ownership.

The implementation may choose the safe ordering of side operations, but every ordering must yield the same committed journal, profiles, ownership map, discovery state, receipts, and history. A committed journal is never rolled back to the original owners in a way that can duplicate a transferred unit. Any precommit rollback must restore exactly the original map and prove that no committed destination ownership exists.

### Reconciliation Before Writable Play

Profile acquisition identifies unresolved trade IDs from profile locks, processed operations, history or receipt pointers, and the journal recovery index. Before the profile is marked writable, reconciliation reads the authoritative journal and advances or safely resolves every relevant operation.

An orphan provisional lock without a prepared journal cancels and unlocks idempotently after verifying that no prepared record exists. A prepared or settling journal completes the exact remaining side steps. A committed journal repairs missing profile receipt, history, current-ownership projection, and unlock cleanup without reversing ownership. A completed journal replay returns the existing receipt.

If reconciliation is throttled or transiently unavailable, the profile remains in a recovery or read-only maintenance state and may safely leave. It cannot earn, spend, alter inventory, or begin another trade. Bounded retries preserve the same trade and step identities. Session collision, concurrent worker, repeated join, server restart, and shutdown all converge through optimistic journal versions and idempotent profile receipts.

Impossible post-prepare ownership, a conflicting processed receipt, unknown schema, or irreconcilable journal quarantines the affected profiles and items with sanitized support evidence. It never deletes an item, guesses a winner, creates a blank profile, or opens writable play.

### Network, Privacy, Security, and Abuse Boundaries

Every action validates exact type, shape, depth, size, enum, participant, state, revision, hash where applicable, item membership, ownership, quantity, timing, request identity, per-action token bucket, and global burst state. It rejects nonfinite numbers, negative or fractional quantities where integers are required, oversized offers, excessive nesting, duplicate IDs, unknown IDs, stale trade IDs, foreign instances, and impossible transition order.

Request IDs and trade IDs provide idempotency and correlation, not authentication. Participant identity, session, permissions, state, ownership, rate, and timing are always revalidated. A modified client cannot choose another participant's item, set value, force Ready, shorten countdown, create a journal, set a step, mark a receipt, or invoke recovery.

Messages are participant-scoped. Unrelated players receive no invite detail, offer, copy count, connection state, journal, receipt, or history. Support views require a separate audited permission path and return only the minimum participant IDs, trade and receipt IDs, stable item identities or hashes, state, timestamps, revisions, error codes, and settlement evidence needed to investigate. Analytics uses bounded counts and bands rather than full offers.

No player-entered trade text exists. Fixed localized UI copy, stable item display names from catalogs, and server enums are the only text sources. Logs and evidence exclude credentials, raw profiles, private logs, authentication data, full inventories, arbitrary strings, and exploit instructions.

Scam friction reduces accidental acceptance but does not promise fraud prevention or item value. Opt-out, expiry, cooldown, exact two-sided review, offer-change reset, five-second countdown, only-copy warning, material-asymmetry warning, immutable receipts, history, and report-by-receipt are mandatory. Security signals cannot create irreversible punishment from one uncorroborated event.

### Feature Flags, Emergency Disable, and Trade Readiness

`TradeEnabled` is fetched from versioned server configuration, cached with a safe false default, included in diagnostics, and projected to clients as an authoritative feature state. False means no new request, accept, edit, Ready, countdown, prepare, lock, or settlement outside prepared-journal reconciliation may begin. Existing transient pre-prepare sessions cancel and release. Prepared-or-later reconciliation remains enabled through a separate nonpublic recovery capability that cannot be switched off by the player-facing flag.

A stale, missing, malformed, incompatible, or unreachable feature configuration resolves to false for new trading. A live true-to-false change stops new work and cancels transient sessions; it does not abandon a prepared journal. Phase 006 never performs a false-to-true change. Phase 009 may do so only after startup validation, current evidence, environment authorization, the frozen readiness record, exact `EXT-011` scope, and the production smoke all pass for the same candidate.

The Phase 006 trade-readiness record has exactly two valid states:

- `enablement_candidate`: every mandatory Phase 006 test and isolated workflow passes for the frozen candidate, no mandatory defect exists, all evidence is current, and the feature remains false pending the Phase 009 `EXT-011` authorization and production smoke.
- `visibly_disabled`: every mandatory Phase 006 implementation, recovery, security, accessibility, and isolated-runtime gate passes, the feature remains false, the UI clearly states that trading is coming later, every new mutation entry point rejects, no new lock or journal can begin, and reconciliation remains active.

Later source, configuration, schema, feature, artifact, environment, permission, runbook, or evidence changes invalidate the readiness record. Invalidation forces `TradeEnabled` false and requires the complete affected Phase 006 chain to pass before either readiness state can be reissued. It also invalidates any dependent Phase 009 authorization or smoke evidence.

### Accessibility and Performance

Every required trade control has touch, mouse, keyboard, and controller paths. Exact items, quantities, owner side, warnings, revision change, Ready state, countdown, connection state, disabled state, and receipt use text and symbols in addition to color, motion, flash, sound, particles, or tilt. Controller focus cannot escape the active confirmation surface. Reduced motion and reduced flash replace countdown and completion effects; low graphics uses static item presentation; UI scale and small-screen layout preserve both offers and all warnings.

Trade state is bounded to two participants and twelve entries per side. Offer normalization, hashing, eligibility, and lock checks operate on bounded collections. No per-frame server loop, broad profile scan on each input, DataStore write on every hover or selection, broadcast to unrelated players, or unbounded receipt history is allowed. Persistent writes occur only at defined lock, prepare, settlement, receipt, history, recovery, and cleanup boundaries through owning services. Performance evidence records action latency, prepare latency, settlement latency, recovery duration, journal retries, payload sizes, profile-size deltas, and server work under the eight-player limit.
