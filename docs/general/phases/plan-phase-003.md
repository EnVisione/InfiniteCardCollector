## Architecture and Implementation Boundaries

- Catalog and asset data flow is one-way: versioned source assets and manifest entries build a validated runtime bundle; catalog definitions reference stable asset IDs; the renderer consumes a presentation model and resolved assets; UI consumes controller state. Assets, the renderer, and UI never call persistence or decide ownership, odds, rewards, progression, or score.
- Stable identity remains separate across base identity, form, and instance. A base identity is Deck Set plus rank and suit. A permanent form adds one enabled Edition. A card instance adds Grade, Power Tier, Trait, provenance, flags, and selected unlocked form. No presentation layer may collapse or reinterpret these contracts.
- The 624 forms are compositional products of 156 identities and four enabled Edition IDs. The pipeline must not create 624 unrelated service branches or duplicate ownership records. A reachability graph must prove one unique form key for every valid product and no path to disabled Editions.
- The asset manifest is the sole runtime reference source for phase-owned media. Every enabled entry has stable identity, content hash, provenance, review state, fallback, budget, and consumer references. Missing, invalid, unreviewed, over-budget, or unresolved entries fail closed before gameplay actions are accepted.
- Original source work and runtime exports are distinct. Deterministic build steps may optimize or atlas assets without changing stable IDs or obscuring provenance. Generated output is committed only in declared artifact locations and is never hand-edited.
- Preload remains bounded to the opening table, current Deck Set frame, basic sounds, and tutorial UI. Other content loads on demand. Pack pieces, cards, particles, sounds, and UI cells use bounded pools. Binder and inventory surfaces instantiate only visible entries plus configured overscan and recycle cells.
- Pack RNG and all valuable decisions reside on the server. The client sends pack type, operation ID, and later a choice among saved offered IDs. The client never supplies a result, odds, pity, Tier, Trait, Grade, cost, or reward. Presentation timing and animation acknowledgement cannot change committed state.
- Pack operations use `created`, `contents_committed`, `revealed`, and `claimed`. Deck Set Packs commit all five grants. Joker and Arcana Packs remain pending after reveal until one valid offered ID is chosen. Replays return the original result; conflicting payloads fail without mutation.
- Progression, Arcana, binding, salvage, flags, and slot edits use the Phase 002 transaction boundary, expected revision, eligibility checks, compact receipts, and immediate-save triggers where required. Services communicate through typed methods and domain events and never mutate another service's internal tables.
- Grade is monotonic stored progress. Balance versions may change future thresholds but cannot lower a saved Grade or delete XP. Edition unlocks and discovery are permanent. Tier and Trait changes obey explicit non-lowering or confirmed-replacement rules. Rejected and interrupted operations preserve the exact prior state.
- Arcana application accepts one saved Arcana stack item or count, one eligible target UID, one action-specific option when required, one operation ID, and one expected revision. Server preview and commit share one pure evaluator. The server consumes exactly one only after the committed result is durable.
- Salvage protection is evaluated at commit time, not only when a button is shown. Favorites, wishlists, locks, active deck items, trade locks, active transformation targets, pending operations, last currently owned copies, and new best records remain protected under stale clients and concurrent actions.
- Every Joker definition references a registered handler and parameters. Handlers execute only at declared Phase 001 stages, write normalized trace entries, declare additive or multiplicative groups, conflicts, precedence, and caps, and cannot mutate persistent state during pure calculation. Persistent counters or rewards use explicit server events and transaction operations.
- A five-slot Joker loadout is server validated and atomically projected to score consumers. Slot six, duplicate UID use, foreign ownership, unavailable content, and locked or bound-state violations fail without changing the previous valid loadout. Duplicate binding is a separate confirmed mutation and never automatic.
- Client controllers render authoritative complete snapshots and narrow patches, keep request IDs and pending state, ignore stale responses, request narrow refresh on conflict, and never convert animation completion into mutation success. Later-phase service surfaces expose disabled or unavailable states until their server owners exist.
- Shared semantic actions map to touch, mouse, keyboard, and controller without requiring device-specific business logic. Focus order, escape or back behavior, confirmation, cancellation, sorting, filtering, scrolling, and recovery are explicit. Motion, flash, sound, particles, tilt, and color are never the only carriers of meaning.
- Phase 003 measures and enforces its declared asset, preload, pool, visible-cell, frame, allocation, memory, and payload budgets. This phase cannot claim the complete eight-player or external cohort performance contract owned by Phase 008.
- Final public brand clearance is not inferred from original content completion. Candidate icon, thumbnail, and metadata composition may be built and reviewed, but Phase 009 must bind the owner-selected final identity and `EXT-007` evidence before release freeze.
