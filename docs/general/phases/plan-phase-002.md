## Purpose and Ownership

This phase delivers the first durable, server-authoritative InfiniteCardCollector vertical slice. A blank account must acquire one writable session, load or create a version 1 profile without unsafe overwrite, open one committed Classic Starter Pack, own five uniquely identified cards with immutable provenance, equip valid cards into the fifty-two-slot deck, submit one guided formation through the Phase 001 calculation contract, receive one idempotently committed reward, disconnect at every durable boundary, rejoin, and recover the exact committed state. The same slice proves the reusable layered card renderer across its initial 2D and 3D surfaces.

The phase canonically owns `CORE-REQ-004`, `CORE-REQ-005`, `CORE-REQ-006`, `CORE-REQ-007`, and `CORE-REQ-008`. It establishes the network, profile, migration, transaction, inventory, collection, deck, and renderer contracts on which every later economy and gameplay service depends.

The master plan owns product scope, requirement meaning, global phase order, owner decisions, external prerequisites, and the plan-wide completion endpoint. This file owns only the dependency-ordered execution of `CORE-PHASE-002`. It cannot alter `DEC-008`, `DEC-009`, the launch content boundary, the protected plan set, or later-phase acceptance criteria.

## Architecture and Implementation Boundaries

The source boundaries from the launch foundation remain authoritative. Shared catalogs and calculations live under `ReplicatedStorage/Shared`; network actions, errors, schemas, and shared types are data and pure validation contracts; authoritative services live under `ServerScriptService/Server/Services`; server-controlled fixture assets live under `ServerStorage/Assets`; and client controllers and UI render server state under `StarterPlayerScripts/Client` and `StarterGui/App`. Pure Phase 001 calculations cannot access DataStore, remotes, UI, or mutable services. Client code cannot access profile storage or decide trusted results.

The server data flow is ordered:

1. `ClientAction` receives a versioned envelope containing only action, request identity, and action payload.
2. The gateway applies global envelope, encoded-size, nesting, scalar, string, collection, finite-number, and unknown-field rules before action lookup.
3. The registered action applies its exact schema, permission, profile readiness, writable-state, expected revision, ownership, timing, spatial, independent token-bucket, and retry rules.
4. Read-only actions call typed service methods and return bounded snapshots or patches. Economy and deck mutations enter `TransactionService` with a normalized payload fingerprint and the same durable operation identity.
5. The transaction boundary serializes mutations for one profile, checks the session token and preconditions, applies through owned service APIs, records the receipt and recoverable result, advances revision, and persists through `ProfileService` and `UpdateAsync` before reporting success.
6. `ServerMessage` returns only the requesting player's necessary result or a deliberately public projection. Unrelated inventory, hidden hands, raw profiles, credentials, arbitrary client text, and internal lock material are never returned.

The launch action registry must cover `bootstrap.request`, `pack.open`, `pack.choose`, `deck.equip_card`, `deck.unequip_card`, `joker.equip`, `joker.unequip`, `arcana.apply`, `grade.apply_ink`, `inventory.set_flags`, `formation.start`, `formation.redraw`, `formation.submit`, `task.start`, `task.action`, `duel.invite`, `duel.respond`, `duel.submit`, `trade.request`, `trade.respond`, `trade.set_offer`, `trade.set_ready`, `trade.cancel`, and `binder.page`. A registry entry declares concrete integer bounds and token-bucket values in versioned configuration, with boundary fixtures at below, exactly at, and above each limit. Later-phase actions have schemas now but route to a stable fail-closed unavailable or disabled result until their owning service is implemented. Unknown action IDs never reach service code.

Stable error codes are lowercase compatibility identifiers grouped around envelope, schema, bounds, rate, readiness, permission, ownership, stale state, request conflict, session, storage, unavailable feature, and internal fail-closed outcomes. The implementation freezes exact codes and their safe response shapes in `P002-TASK-002`. Display text is localized presentation and is not used as the machine contract. Validation order must be deterministic so identical invalid input yields the same public code while logs retain only bounded sanitized context.

Profile version 1 preserves the readable domain fields specified by the launch foundation: schema and revision metadata; timestamps and active seconds; eight currency balances; card and Joker instances; Arcana stacks and reserved Souls state; active deck, Jokers, and Soul; discovered forms, Jokers, Arcana, and Souls; best records; pity; pending packs; boosts; daily and tutorial state; trade history; processed operations; settings; and moderation state. The compact saved representation is separate. Stored field abbreviations, discovery encoding, and receipt compaction cannot leak into gameplay service APIs or reinterpret a stable ID.

`ProfileStore` owns core profile acquisition and persistence. `InventoryStore` is the interface boundary for current inventory even while launch uses one physical profile document. No launch code may assume that inventory remains in one key, because later journaled sharding must replace storage without changing gameplay service APIs. MemoryStore may assist ephemeral presence but cannot own an item, receipt, pending result, migration, or replay barrier.

Each writable profile has one session token containing the relevant place version, job ID, and heartbeat time. Acquisition and every durable write use `UpdateAsync` to compare ownership and revision. Mutations for one profile are serialized. A healthy token rejects a second writer. An expired token requires a fresh read, pending-operation or journal reconciliation, and an atomic reassignment. A heartbeat mismatch immediately closes the mutation gate and enters read-only safe mode. Ordinary dirty writes may batch near the configured interval, while pack commitments, rewards owned by this slice, and other transaction boundaries save before success is returned.

Migrations are pure functions from one declared schema version to the next. They do not read time, random values, DataStore, catalogs with mutable iteration order, or network state. Reapplying the current normalization yields byte-equivalent domain state. Missing or malformed required data is quarantined with a stable diagnostic and never replaced by a blank profile. Every migration preserves ownership, currencies, discovery, pending packs, and processed-operation or receipt state.

The operation layer distinguishes the untrusted client request ID from the server's durable mutation identity. The action registry declares whether a request is read-only, ephemeral-idempotent, or durable-idempotent. A durable receipt retains enough normalized input identity and committed output or a stable output reference to return the exact result. Compaction may remove presentation detail only after a durable replay barrier remains; retention or expiry cannot make the same old operation executable again. A repeated operation with a different fingerprint fails without state change.

Every card and Joker UID is opaque, server generated, checked for collision against current ownership and relevant pending state, and retried without overwriting on collision. Provenance records stable origin type, origin ID, creation time, and instance version and cannot be rewritten by equip, migration, balance change, renderer state, or retry. Inventory is the sole current-ownership authority; collection discovery is permanent history and cannot be used to fabricate current ownership.

The active deck is a map over exactly the Cartesian product of thirteen stable face-rank IDs and four stable suit IDs. A card may occupy only its own `<faceRankId>:<suitId>` slot, and the same UID cannot occupy two slots. Equip and unequip are transaction operations that change loadout references only. They do not create, delete, transfer, or alter the card instance. Locks, active transformation hooks, disabled-content policy, stale revision, and ownership checks run before mutation.

The renderer consumes an immutable authoritative card presentation projection, never profile tables or remote results directly. Its ordered layers are Deck Set frame and illustration, suit treatment, rank and pips, Edition, Grade, Power Tier, Trait, and status overlays. The 2D and 3D adapters interpret the same view model. Status uses text or symbols in addition to color, motion, sound, particles, tilt, or material. Low graphics substitutes static frames for particles and animated gradients. Reduced motion and flash remove nonessential animation without hiding state. Pools recycle 3D cards and effects; virtualized lists render only visible binder entries; preload is bounded to the slice's opening table, current Classic frame, basic sounds, and minimal UI.

The vertical slice uses ordinary data and services. The Classic card, pack, five instances, slot keys, score, trace, and reward cannot use a hard-coded bypass around catalogs, inventory, transaction, renderer, or network contracts. The minimal Formation service orchestrator may own transient guided hand state but cannot write the profile directly. The full timed round, redraw, streak, reward cadence, all-task integration, and onboarding sequence stay closed until their later phases.

## Failure, Recovery, and Edge Cases

| Scenario | Detection | Required behavior | Recovery or rollback | Regression proof |
|---|---|---|---|---|
| Unknown action or incompatible envelope | Registry miss or version mismatch | Reject before routing with a stable bounded error and no mutation | Client receives supported refresh or unavailable state; server retains sanitized action evidence | Every unknown and incompatible fixture leaves profile, revision, and rate state as specified |
| Malformed or hostile payload | Type, field, depth, size, finite-number, enum, string, collection, or integer rule fails | Reject deterministically before service mutation | Return narrow error or state refresh; add only bounded security evidence | Wrong-type, missing, extra, over-limit, `NaN`, infinity, negative, fractional, duplicate, and foreign fixtures for every action |
| Independent or global rate exceeded | Token bucket lacks capacity | Reject without mutation; disclose only stable retry information allowed by the contract | Refill under injected monotonic clock; never queue an economy action for later mutation | Below, at, and above capacity and refill tests for every action plus global burst |
| Stale expected revision or stale request state | Expected revision, round, pending result, or request fingerprint differs | Reject without consuming, equipping, scoring, or rewarding | Return the narrow current revision or state needed to retry with a new deliberate action | Reordered and stale fixtures with exact no-change hashes |
| Identical request or operation replay | Existing request entry or durable receipt has matching fingerprint | Return the exact committed result and do not mutate again | Reopen persisted result after disconnect or response loss | Duplicate and post-rejoin replay returns matching result and revision |
| Conflicting request ID reuse | Existing identity has a different normalized fingerprint or action kind | Reject as conflict without state change | Client must submit a new request only for a genuinely new intent | Conflicting payload property tests and before or after equality |
| Profile cannot load or decode | DataStore error, unsupported schema, malformed required field, or failed migration | Never create a blank overwrite; show retry and safe leave | Bounded retry, then quarantine evidence and maintenance state | Malformed and unavailable-store fixtures preserve original stored bytes |
| Healthy session collision | Existing token heartbeat is within healthy window | Refuse the second writable session | Existing writer continues; second client receives safe retry or leave state | Two-server acquisition fixture proves only one writer and one revision sequence |
| Expired session collision | Heartbeat exceeds expiry threshold | Do not write until recovery read and pending work reconciliation complete | Atomically acquire a new token only after reconciliation succeeds | Expired-lock, pending-operation, and reassignment trace |
| Session ownership lost mid-session | Heartbeat or write token no longer matches | Enter read-only safe mode immediately and stop new rewards and mutations | Preserve client viewing, retry safe reacquisition only through the declared lifecycle, or allow safe leave | Forced token replacement proves no mutation after loss and no overwrite |
| DataStore throttle or transient write failure | Adapter returns retryable service error | Retry only the same idempotent write with bounded exponential backoff and jitter | On exhaustion, preserve last durable state and enter read-only safe mode | Inject failure before each retry and compare durable profile, lock, and revision |
| Migration repeated or interrupted | Current schema is reapplied or failure occurs between load and save | Produce the same normalized profile or leave the prior durable document untouched | Retry the same pure migration; quarantine deterministic failure | Old, current, repeated, and interrupted migration hashes preserve all permanent fields |
| Profile exceeds size budget | Encoded byte measurement crosses warning or block threshold | Warn at `1,000,000`; fail the phase publication gate above `1,500,000` realistic bytes | Reduce representation without deleting data or changing service APIs; rerun all round trips | Stress-size reports and equality after compaction |
| UID generator collision | Candidate UID already exists in inventory or pending state | Generate another UID; never overwrite, merge, or reuse provenance | Bounded retry then fail the operation before commit if uniqueness cannot be achieved | Deterministic forced-collision sequence and unchanged ownership on exhaustion |
| Foreign or duplicate instance ID | Ownership lookup fails, owner differs, or request repeats a UID | Reject before deck, inventory, formation, or flag mutation | Return narrow authoritative state; record bounded reason code | Every inventory-bearing action tests another player's UID and duplicate arrays |
| Illegal deck edit | Slot mismatch, same UID in multiple slots, ineligible or disabled item, lock, stale revision, or nonownership | Reject atomically and preserve ownership and deck | Client refreshes exact slot and instance projection | Exhaustive slot, duplicate, lock, stale, foreign, and disabled fixtures |
| Starter Pack precommit failure | Failure before profile and receipt commit | Keep blank ownership and starter entitlement unchanged; reveal nothing | Retry the same operation ID and inputs | Failure injection before validation, creation, receipt, and save with prior-state hash |
| Starter Pack committed but response lost | Durable pending result and receipt exist, client has no acknowledgement | Never reroll or create another card; reopen exact five results | Rejoin or retry returns the same UIDs, provenance, catalog version, and result hash | Disconnect after commit and before response, then exact recovery comparison |
| Catalog changes while pack is pending | Pending catalog version differs from current | Preserve the exact committed stable IDs and result; do not reinterpret ownership | Render preserved result with compatible fallback or block only unsafe presentation | Pending fixture survives catalog-version change without reroll or deletion |
| Transaction interrupted after mutation staging | Failure occurs before durable atomic commit | Expose no success and preserve prior durable balances, inventory, deck, and revision | Retry same operation from prior durable state | Stage-by-stage failure adapter and conservation hashes |
| Transaction committed before acknowledgement | Receipt and revision are durable but response is lost | Return committed result on retry; never apply delta again | Rejoin reads receipt and pending result | Reward, deck, and pack postcommit response-loss fixtures |
| Receipt compaction or retention boundary | Receipt reaches compaction or expiry policy | Preserve a durable replay barrier and enough result identity for the declared retry contract | Compact safely or move behind storage interface; never delete the only replay proof | Replay immediately before and after every retention boundary cannot mutate twice |
| Shutdown with active mutations | Mutation gate closes or shutdown deadline begins | Stop new actions, finish durable work or preserve an exact pending operation, save dirty profiles, and release sessions within the window | Rejoin reconciles the pending state before writable play | Shutdown injected at every pack, deck, and reward stage plus lock-release timing |
| Renderer receives missing or disabled presentation data | View-model validation or asset lookup fails | Show a neutral readable placeholder without inventing ownership or hiding status | Disable only unsafe acquisition or presentation path; retain diagnostics | Missing-layer and disabled-content golden fixtures in normal and low graphics modes |
| Large binder fixture | Visible component count, allocations, or frame work exceed the declared budget | Render only the visible window and recycle cells and 3D objects | Reduce effects or page size without reducing information | Large-fixture component, allocation, pooling, and virtualization measurements |
| Impossible stored ownership or currency | Duplicate effective owner, invalid provenance, negative balance, or impossible revision is detected | Quarantine affected profile and stop writable play; never silently delete or normalize away value | Preserve sanitized evidence and use an approved reconciliation path later | Corrupt-state fixtures prove fail-closed behavior and byte preservation |
