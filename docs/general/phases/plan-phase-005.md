## Purpose and Ownership

This phase delivers Friend Clash as a safe, repeatable, same-server friend activity. Two eligible players must be able to invite or decline, snapshot their current loadouts, complete an authoritative best-of-five match in Power or Fair mode, reconnect or abandon under deterministic rules, receive only bounded eligible rewards, and rematch without rewards after anti-farming caps apply. The match cannot charge an entry cost, accept a stake, transfer inventory, expose an opponent's hidden hand or private collection state, or write an unsupported rating.

The phase canonically owns `CORE-REQ-019`. It integrates the deterministic calculation contract, typed network gateway, deck and inventory authority, economy and anti-farming configuration, Formation Rush rules, responsive client surfaces, transaction receipts, analytics hooks, and security evidence delivered by earlier phases. It produces the stable two-client social harness required by direct trading in `CORE-PHASE-006`.

The master plan owns product scope, requirement meaning, global topology, owner decisions, external prerequisites, and the completion endpoint. This file owns only the dependency-ordered execution of `CORE-PHASE-005`. It cannot promote spectators, cross-server matchmaking, public ratings, wagering, trading, custom player text, or any future social system.

## Phase Contract

### CORE-PHASE-005 — Authoritative Same-Server Friend Clash

**Objective:** Deliver Power and Fair Friend Clash so two eligible same-server clients can invite, decline, accept, snapshot loadouts, complete a deterministic best-of-five match, time out, tie, disconnect, reconnect, abandon, rematch, and reach reward caps without stakes, transferred ownership, hidden-state leakage, unsupported rating changes, or a mandatory defect.
**Owner:** Duel service
**Dependencies:** CORE-PHASE-004, EXT-012
**Canonical requirements:** CORE-REQ-019
**Documentation and release impact:** Update the root feature status only after the flow is implemented; update `docs/README.md`, `docs/general/documentation.md`, and `docs/implementation/launch-foundation.md` where verified behavior differs from proposed detail; add focused Friend Clash test, verification, security, accessibility, performance, moderation-evidence, operations, and troubleshooting records. Do not publish or widen Roblox access in this phase.
**Next transition:** `CORE-PHASE-006`

**Entry criteria**

- The complete protected plan set and saved goal exist, every recorded digest matches, and the goal identifies `CORE-PHASE-005` as the first unfinished mandatory phase.
- `CORE-PHASE-004` is merged into `main` through GitHub, required checks and review are resolved, its signed annotated tag is pushed, `origin/main` contains the merge commit, and the Phase 005 branch starts from that exact commit.
- The Phase 004 completion packet proves the authoritative Formation Rush round, deterministic hand and score paths, responsive controllers, device inputs, reconnect handling, reward transaction boundary, analytics boundary, and configuration consumers on which Duel service depends.
- Phase 001 through Phase 004 contracts remain green for exact catalogs, score traces, network schemas, profile sessions, operation receipts, inventory ownership, deck snapshots, Joker effects, Formation Rush, client rendering, documentation, build, Studio synchronization, and artifact integrity.
- The versioned Duel configuration declares and validates invite expiry, action token buckets, global burst behavior, round deadline and latency tolerance, reconnect grace, reward amounts, reward reason IDs, daily cap, per-opponent window and diminishing schedule, rematch eligibility, feature controls, and all required maximum collection sizes. The invitation expiry is exactly thirty seconds. Missing or invalid values fail closed.
- `EXT-012` provides consented duel participants, dedicated eligible and ineligible duel account roles, and the representative phone, tablet, desktop, touch, mouse, keyboard, controller, reduced-motion, reduced-flash, color-assistance, low-graphics, and UI-scale coverage needed for real-workflow proof. If unavailable, implementation and lower-fidelity tests may not be misreported as phase completion.
- No source or configuration change introduces spectators, cross-server matchmaking, public ratings, trading, wagering, custom player text, or client-trusted score or reward input.

**Implementation scope**

- CORE-REQ-019: Define the Duel domain model, mode and result enums, invitation, match-session, round, submission, connection, reward-eligibility, and terminal-state contracts with opaque server-generated session and round IDs. Register `duel.abandon` as a typed participant intent alongside the upstream `duel.invite`, `duel.respond`, and `duel.submit` actions.
- CORE-REQ-019: Implement same-server invite eligibility, incoming duel-request opt-out, exclusive pending and active state, thirty-second expiry, decline, cancellation, per-action token buckets, a global burst limit, cooldown responses, and stable no-penalty outcomes.
- CORE-REQ-019: Snapshot each accepted participant's active deck, active Jokers, legal effect data, and required catalog, configuration, and calculation versions without locking or transferring ownership. Match play uses the immutable snapshot even if the live loadout changes later.
- CORE-REQ-019: Derive deterministic server-only round inputs from the match seed, participant side, round index, snapshot, catalog version, and configuration version. Both players receive the same public prompt; their hands are independently shuffled as required by the launch contract.
- CORE-REQ-019: Run at most five scheduled rounds and stop early when a player wins three. Each valid round submission is final and hidden from the opponent until both valid submissions arrive or the deadline resolves. Arrival order cannot change hands, traces, round result, match result, or rewards.
- CORE-REQ-019: Resolve each submitted round simultaneously. If only player A's Power is greater than player B's Guard, player A wins the round. If only player B's Power is greater than player A's Guard, player B wins. If both breach or neither breaches, the round is a draw. A draw consumes the scheduled round and awards neither player a round win. If neither player reaches three wins after round five, the match result is `draw`. If one player submits before the authoritative deadline and the other does not, the non-submitter loses that round. If neither submits, the round is a draw. Late and stale submissions fail without changing the resolved result.
- CORE-REQ-019: Evaluate Power mode from the full accepted snapshot. Evaluate Fair mode by normalizing Grade, Power Tier, and Edition numeric multipliers only, preserving card identities, legal choices, formations, Traits, and every Joker with an explicit Fair-compatible rule. A missing or ambiguous Fair classification fails closed before the match starts.
- CORE-REQ-019: Produce deterministic internal score traces, player-owned detailed traces, and opponent-safe public result traces. Do not reveal an opponent's hidden hand, unused cards, future draw order, full snapshot, inventory, profile, or private calculation inputs.
- CORE-REQ-019: Pause an eligible active match for the configured same-server reconnect grace. Before round two begins, disconnect or abandon cancels all rewards. After round two begins, grace expiry or deliberate abandon produces the configured forfeit result; the abandoning player receives no reward, and any opponent reward remains subject to every anti-farming gate.
- CORE-REQ-019: Commit eligible rewards once through Transaction service using a server-derived match result operation identity. Duel Tokens and any already-configured first-daily Friend Clash bonus are the only permitted phase-owned economy outputs. No entry deduction, stake, item grant, item move, currency transfer, rating reward, or client-supplied amount is permitted.
- CORE-REQ-019: Enforce durable daily and per-opponent diminishing caps from trusted server time. When a cap or reward feature disable applies, the match remains playable as a private no-reward rematch and the UI explains reward ineligibility before the next match begins.
- CORE-REQ-019: Implement accessible Friend Clash presentation, sanitized duel analytics, bounded security and moderation evidence, feature-disable behavior, no-rating boundaries, and duel-specific performance instrumentation.

## Architecture and Implementation Boundaries

### Ownership and Dependency Direction

`DuelService` owns invitations, participant exclusivity, immutable match snapshots, session and round state, authoritative deadlines, connection state, simultaneous resolution, match results, reward eligibility, and terminal cleanup. It calls typed calculation, Formation, Deck, Joker, Transaction, Analytics, and Security interfaces. It does not reach into another service's mutable tables, write profiles directly, move inventory, settle trades, write leaderboards, or trust client state.

The network gateway validates Duel envelopes before routing. The client controller submits intent and renders server messages. The Friend Clash UI cannot infer acceptance, hands, score, timeout, reward, cap, rating, or reconnect success from animation or local time.

### Invitation Eligibility and Opt-Out

An invitation is eligible only when the activity accepts new requests, inviter and target are distinct players currently present in the same server, both profiles and bootstrap state are fully loaded and writable, both clients support the current Duel contract, both loadouts can produce a legal snapshot for the requested mode, neither participant has an exclusive pending invite or active match, the target permits incoming Duel requests, upstream block or social-policy state permits the interaction, and the inviter has available action and global rate capacity. The server evaluates every condition at invite and revalidates both participants at acceptance.

The incoming-request setting controls unsolicited invitations without publishing why a target is unavailable. A player who opts out may still initiate a request if otherwise eligible. Decline, opt-out, expiry, ordinary busy state, and unsupported-mode rejection carry no gameplay penalty, rating change, or abuse signal. Security evidence is reserved for malformed, impossible, conflicting, or abusive action patterns rather than ordinary social choices.

### State and Identifiers

Invitations and active matches are transient server state. A server-generated opaque invitation ID identifies one inviter-target request. A server-generated opaque session ID identifies one accepted match. Each scheduled round has a session-bound round ID and index. Every action also carries its ordinary request ID. IDs are not secrets and never substitute for participant, state, rate, ownership, or timing validation.

The accepted snapshot contains the ordered active deck, active Jokers, legal calculation inputs, and catalog, configuration, calculation, and snapshot schema versions. It is immutable for the match and does not lock ownership. A later live deck edit cannot change the accepted match, and the snapshot cannot grant ownership or become an inventory authority.

The session state is bounded to two participants, at most five scheduled rounds, eight cards per hand, one-to-five submitted cards, a bounded score trace, one final submission per participant per round, and one terminal result. No unbounded history or client payload is retained.

### Determinism and Simultaneous Resolution

The server owns seed material and derives the shared public prompt and each participant's independent hand from stable ordered inputs. Identical snapshots, participant sides, round index, catalog version, configuration version, and seed produce identical hands and traces regardless of table iteration, message delivery, submission arrival, animation timing, or reconnect.

A valid submission becomes final but remains hidden from the opponent until both valid submissions exist or the deadline adjudicates the round. Resolution uses one serialized transition. If actions arrive on the boundary, the authoritative server receive time and configured latency tolerance decide acceptance. A late action cannot reopen a resolved round.

For a round with two valid submissions, the evaluator compares each participant's Power against the opponent's Guard. Exactly one breach produces that participant's round win. Two breaches or zero breaches produce a draw. Equality is not a breach. Timeout adjudication occurs before this comparison and follows the explicit one-submitter or no-submitter rules. This rule is identical in Power and Fair modes after their respective score inputs are calculated.

Drawn hands are private. After resolution, the opponent-safe projection may show the submitted cards, formation, Power, Guard, round outcome, and bounded explanation required to understand the result. It cannot show unused cards, future draw order, full snapshot, private effect inputs, inventory counts, profile fields, or settings.

### Mode Boundaries

Power mode evaluates the accepted snapshot through the ordinary deterministic score stages with owned Grade, Power Tier, Edition, Trait, affinity, Joker, and other enabled launch rules.

Fair mode substitutes normalized numeric components only for Grade, Power Tier, and Edition. Card identities, legal formation choices, Traits, and explicitly compatible Joker rule interactions remain. Every Trait and launch Joker that can participate must have a documented deterministic Fair classification. An unsupported or ambiguous interaction disables Fair match start with a stable error; it never silently changes rules.

Neither mode writes rating in this phase. Same-server friend games do not provide the population or matchmaking contract needed for a meaningful public rating. Rating UI and boards remain hidden, and `LeaderboardService` receives no Duel write.

### Rewards, Persistence, and Anti-Farming

The live match is transient. Only the final reward operation, durable daily or per-opponent anti-farming state, resulting currency balance, and compact receipt persist. The server derives the reward operation identity from the authoritative match result. Client-supplied amounts, opponent keys, timestamps, caps, rating, or eligibility are rejected.

Per-opponent state uses a bounded server-owned opponent key and trusted time. It records only the minimum counter and expiry data required by the configured diminishing window. Daily state uses the configured trusted day boundary. Both survive reconnect and server changes without unbounded profile growth. At or beyond either cap, private rematches continue with a zero-delta receipt or explicit no-mutation result as defined by the transaction contract.

No Duel operation removes currency, transfers currency, creates or moves a collectible, changes ownership, locks inventory, invokes Trade service, or awards winner-take-all value. Duel Tokens are nontransferable. Any configured first-daily Friend Clash bonus remains an ordinary server-configured bounded grant with its own stable reason ID.

### Feature Controls, Security, and Moderation

The server configuration has safe defaults for accepting new Friend Clash invitations and for issuing Friend Clash rewards. Disabling new clashes rejects new invitations and terminates or cancels unresolved sessions without reward under a stable disabled state. Disabling rewards preserves private play and committed receipts but makes every uncommitted result reward-ineligible. A feature change never deletes currency or ownership.

Every Duel action validates exact types, sizes, enums, participant identity, current invitation or session, round ID, round state, submission membership, duplicate IDs, timing, request replay, per-action rate, and global burst state. Impossible actions create bounded stable security evidence, not an irreversible punishment from one signal.

Invites, decline reasons, results, and rematches use fixed localized copy and server enums. No free-form note, name, or custom text crosses the Duel action or message boundary. Restricted moderation evidence may reference participant IDs, session and round IDs, versions, stable result or security codes, and timestamps needed for review. Analytics and opponent messages receive no raw participant identifiers, hidden hands, full traces, inventory, profiles, or arbitrary text.

### Accessibility and Performance

Every required control has touch, mouse, keyboard, and controller paths. Timers have text and non-color progress, selection and submission have text and symbols, controller focus cannot escape the active modal surface, and status does not depend only on motion, flash, sound, particles, tilt, or color. Reduced motion and reduced flash replace intense transitions; low graphics uses static card and result effects; UI scale and small-screen layout preserve mode, timer, formation, score, reconnect, cap, and confirmation details.

The server supports the initial eight-player limit and therefore at most four concurrent two-player matches. Duel work is event-driven and bounded by two snapshots, five rounds, eight-card hands, five submitted cards, fixed trace limits, fixed message ceilings, and configured cleanup deadlines. There are no per-frame server loops, DataStore writes per input, broad inventory scans during submission, or broadcasts to unrelated players. Analytics and saves are batched through their owning services.
