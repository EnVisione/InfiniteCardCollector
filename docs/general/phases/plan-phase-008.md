## Purpose and Ownership

This phase turns the complete implemented product into one frozen, auditable release candidate. It proves that required play remains usable across representative devices and input methods, that accessibility settings preserve meaning and confirmation safety, that the client and eight-player server stay inside recorded budgets, and that security, persistence, transactions, migrations, recovery, commerce, social systems, artifacts, operations, documentation, and manual experience withstand release-level regression.

The phase canonically owns `CORE-REQ-023` and `CORE-REQ-024`. It verifies every earlier mandatory requirement at its deterministic layer and at the highest-fidelity applicable Roblox workflow, but it does not take product ownership away from the component that implemented that requirement. A defect found here returns to the owning component for a focused correction on the Phase 008 branch, creates a new candidate identity, invalidates affected evidence, and is then retested from the lowest changed layer upward.

The master plan owns product scope, requirement meaning, global topology, owner decisions, external prerequisites, and the public completion endpoint. This file owns only the dependency-ordered hardening, freeze, and evidence blueprint for `CORE-PHASE-008`. It cannot waive a failed gate, convert an unavailable external prerequisite into passing evidence, enable future scope, publish the experience, or mutate a protected plan artifact.

## Architecture and Implementation Boundaries

### Verification Authority and Candidate Identity

The verification system orchestrates checks and records evidence. It does not become gameplay authority, write profile state outside test fixtures, change expected results to match behavior, or bypass component interfaces. Each component remains responsible for its own mutation and recovery contract.

The candidate identity includes the source commit; build and source-map identities; exact tool and Studio versions; catalog, configuration, profile schema, migration chain, action registry, stable error, calculation, asset, product and receipt versions; feature-flag values and safe defaults; Roblox universe and private place identities; runbook digests; and the accepted trade state. The manifest also records SHA-256 and SHA-512 for the built place artifact, source map, asset manifest, product manifest, configuration snapshot, and evidence index. It contains no credential, raw account identity, raw profile, or private participant data.

A manifest is immutable. Any constituent change creates a new candidate ID. Evidence may carry forward only when the invalidation graph proves the changed constituent cannot affect it and the source path, runtime path, environment, and observed output remain identical. A fix that changes an exercised path always invalidates that path and every dependent higher-fidelity workflow.

### Focus, Confirmation, and Semantic Safety

Every controller-capable surface has an explicit directional focus graph. Opening a modal moves focus inside it, background actions cannot fire, cancel and back remain reachable, and close restores focus to the initiating control or the nearest still-valid control. Disabled, hidden, recycled, or destroyed binder cells cannot retain focus. Keyboard-only traversal follows reading order and never requires pointer movement.

Every resource-consuming, ownership-affecting, only-copy, progression-target, purchase, and trade action displays exact target identity, stable item details, exact cost or guaranteed grant, relevant lock or only-copy warning, operation state, confirm and cancel controls, and the authoritative response. Double activation, held input, focus movement during response, animation completion, or stale local state cannot submit a second mutation. A failed or stale response clears or refreshes only the narrow state required and never presents success.

Important rarity, selection, confirmation, warning, lock, favorite, wishlist, new, trade, connection, disabled, maintenance, error, and pending states use readable text plus a distinct icon or symbol. Color, motion, sound, particles, shader, tilt, and spatial position may reinforce meaning but cannot be the sole channel. Reduced settings preserve the same information and action order.

### Rendering, Virtualization, and Join Loading

The card renderer consumes authoritative card presentation data and owns no gameplay decision. Pools have named object classes, configured initial and hard maximum sizes, acquisition and release counters, ownership assertions, and reset rules. Repeated binder, reveal, Formation Rush, duel, and trade navigation must return inactive objects to the pool without retaining player data, focus, event connections, animation state, or references.

The binder and inventory binder render only the visible range plus a numerically bounded overscan declared in the budget manifest. Paging requests remain server validated and payload bounded. Sorting, filtering, resize, scale changes, and rapid direction changes cannot duplicate cells, show stale ownership, lose focus, request an unbounded page, or grow retained objects after steady state.

The join preload allowlist contains only the opening table, current Deck Set frame, basic sounds, and tutorial UI required by the launch foundation. The manifest records asset count, encoded or downloaded bytes where measurable, cold and warm duration, timeout, fallback, and late-load behavior. Full inventory, every card illustration, every rare effect, every Joker prop, and offscreen binder content load on demand and cannot block profile readiness or safe exit.

### Performance and Persistence Boundaries

The numeric budget manifest is versioned and frozen before measurement. For client frame time, server script or frame time, client and server memory, allocation rate, garbage-collection pause, join preload, asset load, action and message payload size, encoded profile size, DataStore operation rate, and eight-player contention it records metric name, unit, device or server tier, workload, warm-up, sample duration, p50, p95, p99 and peak where applicable, numeric threshold, allowed variance, instrumentation overhead, and failure rule. No required field may be recorded as unknown at exit.

The hard profile gates are fixed: warn at `1,000,000` encoded bytes and block publication above `1,500,000` bytes for realistic stress fixtures. Each public action and server message has its own exact byte maximum in the versioned action registry. A generic transport maximum cannot replace action-specific proof. The bootstrap snapshot is paged and private inventory remains least-disclosed.

The eight-player workload includes simultaneous cold joins, warm rejoins, pack reveal overlap, binder paging, all four tasks, Formation Rush, two simultaneous Friend Clashes, and trade settlement or the disabled request path. It runs steady-state and peak-overlap windows, then disconnect, recovery, and shutdown. A result passes only when every percentile and peak rule stays inside its frozen budget and no correctness or recovery invariant fails under load.

Formation detection remains pure and bounded to eight hand cards and five submitted cards. Passive income uses trusted timestamp deltas on a controlled interval. Profile saves are dirty-batched approximately every sixty seconds and immediate only for contractually required transactions. Instrumented call traces must show no DataStore, MemoryStore, transaction save, passive-income mutation, broad inventory scan, analytics flush, or network broadcast initiated by render, heartbeat, or another per-frame callback.

### Security, Persistence, Transaction, and Social Boundaries

The action registry is the source of truth for network fuzzing. Each action receives a generated base corpus and action-specific ownership, permission, state, timing, rate, spatial, and foreign-instance fixtures. The gateway validates before routing. Unknown actions and invalid envelopes cannot reach business services. Stable sanitized reason codes are asserted, but response detail cannot reveal another player's state or give exploit instructions.

Migration fixtures are immutable inputs. Every version-to-current path is pure, forward-only, repeatable, and ownership preserving. Applying the current migration chain twice or more produces the same canonical profile. A malformed or incompatible profile quarantines and prevents blank overwrite. Session collision, stale heartbeat, throttle, retry exhaustion, and shutdown preserve the last durable revision and transition to safe mode or recovery exactly as specified.

Every representative operation uses the original operation ID across retry. Identical replay returns the committed result; conflicting reuse fails. Receipt compaction or expiry cannot make an old operation executable again. Purchase callbacks use the durable receipt identity and exact product definition. Reordering, delay, duplicate delivery, profile migration, restart, or disabled product cannot create a second entitlement or lose the first committed grant.

Trade failure injection enumerates `requested`, `accepted`, `editing`, `a_ready`, `b_ready`, `both_ready`, `countdown`, `prepared`, `settling`, `committed`, `completed`, and `declined`, `cancelled`, `expired`, `rejected`, `rolled_back` terminal paths. At each applicable nonterminal state, stop client A, stop client B, stop the server, fail the next profile write, repeat the last request, reorder two valid requests, attempt every forbidden locked-item mutation, rejoin both players, and reconcile. Each fixture asserts journal state, offer hash, lock state, processed trade IDs, receipt agreement, unchanged currency, and exactly one effective owner for every instance.

### Runbook and Artifact Boundaries

Runbook rehearsal uses the private test environment and synthetic or dedicated test data. It does not widen public access or perform an operation outside existing authorization. Each rehearsal binds candidate ID, runbook hash, environment, operator role, start and end time, allowed operations, expected signals, abort threshold, rollback, state preservation, and collected evidence.

The built artifact and source map are reconciled against an explicit allowlist. Every source-map entry resolves to intended repository source or approved generated metadata. Every artifact asset resolves to the candidate asset manifest and provenance record. The inspection rejects credentials, tokens, private account data, raw profiles, caches, crash logs, debug-only panels or remotes, test fixtures not intended for release, absolute machine paths, editor residue, unrelated files, and unexplained duplicate assets.
