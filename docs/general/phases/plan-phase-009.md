## Purpose and Ownership

This phase converts the verified Phase 008 candidate into the owner-selected public product endpoint. It clears and applies the original final public identity, binds every release-significant identity and runbook, obtains operation-specific authorization, executes the private soft launch, corrects any mandatory defect with complete evidence invalidation, executes the authorized production purchase smoke and conditional trade smoke, widens public access in controlled stages, observes production health and integrity, proves rollback and state preservation, synchronizes canonical documentation and GitHub, and closes the exact plan-wide Definition of Done.

The phase canonically owns `CORE-REQ-025` and `CORE-REQ-026`. It consumes all earlier requirements as frozen release inputs and verifies their production-facing invariants, but it does not redefine their behavior or take ownership from the implementing components. A production finding returns to the owning component for a focused correction on the Phase 009 branch. Any correction that changes an exercised path creates a new candidate identity and invalidates all affected evidence from the lowest changed layer through private launch, production smoke, rollout, observation, documentation, and final audit.

The master plan owns product scope, requirement meaning, global topology, owner decisions, external prerequisites, the trading choice, and the completion endpoint. This file owns only the dependency-ordered execution of `CORE-PHASE-009`. It cannot waive a missing authorization, infer an owner decision, treat an unavailable external prerequisite as passing, weaken a threshold, promote `PLAN-FULL`, modify the live plan set outside a current direct owner-authorized Plan Creator pass, modify the saved goal in any case, or claim completion before the public endpoint and plan-wide Definition of Done are proven.

### Task Ordering, Failure Handling, and Parallel Work

- `P009-TASK-001` is the serial entry gate. A changed saved-goal digest, material product-contract incoherence requiring `PLAN_REVISION_REQUIRED`, missing Phase 008 merge or tag, wrong branch base, incoherent candidate, absent saved-goal authority, or unresolved mandatory Phase 008 defect stops all release work. Authorized plan digest drift alone does not stop entry, and the goal's creation-time active-phase statement is not expected to advance.
- `P009-TASK-002` and the read-only evidence collection portions of `P009-TASK-003` may proceed in parallel after entry, but candidate freeze waits for both. Search evidence, permission evidence, and owner acceptance must identify exact assets and environments rather than placeholders.
- Missing external evidence produces an explicit `NOT COMPLETE — EXTERNALLY BLOCKED` state for the dependent task. Safe documentation, manifest preparation, and nonmutating preflight may continue, but no authorization-bound operation may begin.
- `P009-TASK-004` is a serial freeze gate. The final brand or any release-only change is candidate-affecting. It requires a new candidate ID and every affected Phase 008 deterministic, device, performance, artifact, manual, documentation, and runbook result to rerun before authorization is requested.
- `P009-TASK-005` performs only operations listed by `EXT-008`. An authorization field mismatch, operator mismatch, expired window, different place, or different artifact stops before publication. If access was changed accidentally, restrict it immediately through the approved safe path and retain evidence.
- `P009-TASK-006` is a loop, not a waiver point. A mandatory defect, threshold failure, missing metric, bad sample definition, stale query, unmonitored critical path, or decisive fixable onboarding drop-off yields hold or no-go. The fix runs on the Phase 009 branch, invalidates evidence from the lowest affected layer, and requires new candidate and authorization bindings where identities changed.
- Independent analysis of already captured private evidence may run in parallel, but no concurrent run may share mutable test accounts, operation IDs, receipt identities, trade IDs, DataStore namespaces, or device-session identities. Raw participant data stays outside repository evidence.
- `P009-TASK-007` is destructive production verification and cannot begin without `EXT-010`. A repeated callback uses the same receipt identity. A failed check disables the affected product, preserves the receipt and profile, performs only approved remediation, and blocks public go.
- `P009-TASK-008` branches exactly once on the frozen trade disposition. `enablement_candidate` still defaults to disabled until `EXT-011` and every smoke gate pass. `visibly_disabled` cannot run a production trade and must prove that modified clients cannot start a new request, lock, or journal.
- `P009-TASK-009` starts only after private acceptance, purchase acceptance, final trade disposition, support readiness, moderation readiness, analytics readiness, rollback readiness, and all mandatory environment and product evidence pass. `EXT-009` is rechecked immediately before every audience change.
- `P009-TASK-010` and `P009-TASK-011` widen access serially. A stage cannot begin while the prior stage is inside its observation window, below its frozen sample-quality rule, missing telemetry, under active incident review, or failed. - Production nondestructive checks use dedicated blank and role-specific accounts and stable operation identities. They must not modify unrelated player state or expose private account details in evidence.

- `P009-TASK-013` requires the complete final observation window. A short healthy interval cannot substitute for the authorized window. ## Architecture and Implementation Boundaries

### Release Authority and Immutable Candidate Identity

Release operations orchestrates publication, evidence, access, thresholds, and rollback. It does not become gameplay authority, manually rewrite a profile, settle an item outside the Trade service, grant an entitlement outside receipt processing, change analytics results, or bypass service and permission boundaries.

The immutable candidate identity includes source commit; built place artifact and source map; exact tool and Studio versions; catalog, configuration, calculation, schema, migration, action, error, asset, product, receipt, policy projection, feature-flag and safe-default versions; final public brand and metadata identities; universe, private place, release place, and prior rollback place version; accepted trade disposition; runbook digests; and evidence-index digest. SHA-256 and SHA-512 cover every release-significant artifact named by the manifest.

Any constituent change creates a new candidate ID. Evidence carries forward only when the Phase 008 invalidation graph proves the changed constituent cannot affect the source path, runtime path, environment, operation, observed output, or decision. A fix that changes an exercised path always invalidates that path and every dependent higher-fidelity workflow.

### Authorization Boundary

Each of `EXT-008`, `EXT-009`, `EXT-010`, and conditional `EXT-011` is independent. The authorization record binds exactly:

1. `runbook_digest`.
2. `artifact_identities`.
3. `systems`.
4. `operations`.
5. `operators`.
6. `time_window`.
7. `rollback`.

All seven fields must match immediately before the first operation and remain stable through the authorized window. A changed field voids authorization. A longer window, additional stage, different product, different account, different operator, new trade step, changed metadata, or changed rollback procedure requires a new authorization rather than an execution note.

### Environment, Place, Product, and Publisher Identity

The environment manifest distinguishes the private test place, release place, and exact prior place version available for restoration. It records universe ID, place IDs and versions, owner identity, publisher role, audience state, DataStore namespace, MemoryStore use, PolicyService access, MarketplaceService access, analytics destination, configuration source, product IDs, product regions, feature-state version, and moderation and support routing.

Publisher permissions use least privilege and are tested before the window. The operator who changes access or publishes the place must be named by the authorization. Service smoke tests are isolated and never expose credentials, raw profiles, receipt secrets, private participant identities, or unrelated production state.

### Analytics, Thresholds, and Decision Authority

Analytics events are server emitted, bounded, versioned, sanitized, and reconciled to authoritative receipts and profile revisions. Dashboard queries record event-schema version, candidate ID, place ID and version, feature-state version, population definition, account exclusions, time range, sample-quality rule, aggregation, and last refresh.

The locked healthy thresholds are:

| Metric | Pass threshold | Abort or hold interpretation |
|---|---:|---|
| First pack completion | More than `85%` of joins | At or below threshold after the frozen sample-quality rule is met blocks widening |
| First pack median time | Less than `30` seconds | At or above threshold blocks widening |
| First Formation Rush completion | More than `70%` of joins | At or below threshold blocks widening |
| First Formation Rush median time | Less than `2` minutes | At or above threshold blocks widening |
| Ten-minute first-session retention | More than `55%` | At or below threshold blocks widening after the full eligible window matures |
| Tutorial completion | More than `70%` | At or below threshold blocks widening |
| Pack opening interruption or failure | Less than `0.1%` | At or above threshold blocks widening and triggers pack-path review |
| Successful save sessions | More than `99.9%` | At or below threshold blocks widening and may trigger access restriction |
| Crash-free sessions | More than `99.5%` | At or below threshold blocks widening and triggers crash triage |
| Confirmed item duplication | Exactly `0` | Any confirmed duplication stops rollout and triggers rollback or restriction |
| Trade settlement requiring recovery when enabled | Measured and less than `0.1%` after release | At or above threshold disables new trades and blocks enabled acceptance |

Safety aborts do not wait for sample sufficiency. Any confirmed profile loss, duplication, infinite reward, currency underflow, unsafe receipt, unauthorized remote mutation, private-state disclosure, inaccessible required path, irreconcilable journal, missing critical telemetry, wrong artifact, permission overreach, or authorization breach immediately stops widening and invokes the runbook.

The runbook freezes sample-quality rules, stage populations, and observation durations before the result is known. It may compare day-one, day-seven, co-play, playtime, play days, retention, and monetization with Similar Experiences benchmarks, but those comparisons do not replace or weaken the mandatory thresholds.

### Staged Access and Observation

The public rollout has a preflight state, at least one restricted public stage, and the intended public access state. The exact audience bounds, entry signals, exit signals, observation duration, sample-quality rule, and allowed operations for every stage are frozen in the `EXT-009` runbook. No stage is inferred from a percentage or audience label outside that authorization.

Each stage follows this order:

1. Verify candidate, place, metadata, configuration, feature flags, operator, time window, authorization, dashboards, support, moderation, and rollback readiness.
2. Apply only the authorized audience change.
3. Run the nondestructive blank-profile and critical-path smoke.
4. Observe safety signals immediately and metric gates for the full frozen window.
5. Reconcile analytics, receipts, revisions, support and moderation evidence.
6. Record go, hold, no-go, or rollback with the exact signal and evidence.
7. Widen only after a clean go decision.

### State Preservation and Rollback

Audience restriction and exact prior-place restoration are the primary release rollback controls. Feature controls close unsafe acquisition or mutation paths while preserving committed ownership. Rollback must preserve profiles, currencies, cards, Jokers, Arcana, Grades, Tier and Trait state, discovery, pity, pack contents, pending choices, operation receipts, purchase receipts, entitlements, trade journals, locks needed for recovery, settings, tutorial state, and provenance.

Rollback never creates a blank overwrite, deletes ownership, changes a committed result, settles a trade outside its original journal, replays an operation with a new ID, or silently compensates a player. Affected profiles remain read-only or quarantined until the original receipt or journal reconciles. The approved maintenance state provides a safe retry or leave path and does not advertise an unavailable feature as working.

### Trading Boundary

The default production feature state is disabled until enablement proof is complete. For an enablement candidate, `EXT-011` permits only the exact bounded accounts, disposable instances, offer, replay, disconnect or recovery, ownership inspection, and receipt comparison. The smoke must prove one effective owner, identical journal and receipts, preserved provenance, writable-profile recovery, and correct analytics.

If any gate fails or `EXT-011` is absent, `TradeEnabled` remains false. The booth clearly states that trading is unavailable or coming later, the server rejects new requests with the stable disabled response, no new offer lock or journal can begin, modified clients cannot bypass the state, and prepared journals from prior evidence remain recoverable. That visibly disabled state satisfies `DEC-005`; later enablement belongs to `FUT-015`.

### Documentation and GitHub Boundary

Tracked documentation remains canonical. Execution evidence belongs in ordinary documentation, verification records, Issues, Project items, milestones, pull requests, releases, and wiki navigation. The live plan set changes only through a current direct owner-authorized Plan Creator pass, then execution rereads the complete validated set and deterministic handoff. The saved goal never changes.

There is one GitHub milestone for each of the ten global phases, `CORE-PHASE-000` through `CORE-PHASE-009`. Phase 009 work stays on its sequential `envy/` branch until the pull request passes required checks and review and merges by merge commit. The signed annotated Phase 009 tag targets the merged `main` commit. The wiki is updated only after merge and links back to tracked canonical documentation.
